# CLAUDE.md

Оперативные заметки для Claude-сессий, работающих с этим репозиторием — плотно,
для агента. Не класть сюда реальные серверные пути (raw filesystem-путь сервера
вида `/mnt/1tb-1/cloud/ext-data/...`, реальные WebDAV URL, пароли) — они ДСП, живут
в приватном Google Docs ("TESL — ДСП: серверные пути и структура депо") и в
`%APPDATA%\Uploder\config.json` на машине оператора, не в git. Сверься с TESL/CLAUDE.md
— оба репозитория обязаны говорить на одном depot-протоколе с WebDAV.

## Крэш без единого следа при публикации крупной сборки (Skyrim) — глобальный excepthook + файловый лог (2026-09-23)

**Живой инцидент**: пользователь начал публикацию Skyrim через "🚀
Релизы" (chunk/pack-протокол, см. ниже) — прошёл этап хэширования
(`ChunkManager.scan_directory()`/`scan_components()`, реальная сборка
~171GB/173137 файлов, см. "🔴 Восстановление сборки из чанков" ниже за
подтверждённый реальный масштаб) — и приложение молча исчезло, без
диалога ошибки, без сообщения. Нет ни трейсбека, ни лога — расследовать
конкретную причину по факту было нечем.

**Найдено статическим анализом, без воспроизведения** (не было
крэш-лога, чтобы указать точную строку — вместо гадания вслепую
закрыт САМ КЛАСС проблемы):
1. `.exe` собран `pyinstaller --noconsole --onefile --windowed`
   (`.github/workflows/build-release.yml`) — у собранного приложения
   НЕТ консоли вообще. Любое необработанное исключение, которое не
   поймано существующими try/except (`DepotBuildWorker.run()` в
   `depot_sync_manager.py` уже ловит всё широким `except Exception` —
   ЭТОТ путь и так логировал ошибки штатно, через `log.emit()`) —
   просто гасило процесс, и посмотреть traceback было решительно
   негде: ни `sys.excepthook` не был установлен, ни stderr никуда не
   виден в `--noconsole`-сборке.
2. Даже штатный, успешно отработавший лог (`MainWindow.log_message()`)
   существовал ТОЛЬКО в памяти (`_log_lines`) и в `QTextEdit` —
   `config.LOG_FILE` (`%APPDATA%\Uploder\uploader.log`) был объявлен в
   `config.py`, но НИГДЕ не использовался (`grep -rn LOG_FILE` по
   всему репозиторию — только объявление). Единственный способ
   сохранить лог — кнопка "Сохранить лог" в UI, нажать которую после
   неожиданного крэша уже физически невозможно — весь ход событий до
   падения терялся безвозвратно вместе с процессом.
3. Самый вероятный конкретный триггер (не единственно возможный, но
   структурно самый правдоподобный): `DepotTab._on_scan_done()` — код,
   который выполняется на ГЛАВНОМ потоке сразу после успешного
   завершения сканирования (то есть ровно в момент "хэшировалось —
   и пропало"), строит `DepotConfirmDialog` — самый новый,
   наименее протестированный код в этом пути, для первой публикации
   огромной сборки обрабатывающий сотни тысяч путей (см. докстринг
   диалога — списки файлов там УЖЕ обрезаны до 500/300/200 строк для
   отображения, но полный проход по `d.files_new + d.files_changed`
   для подсчёта `new_bytes` — нет). Этот путь НЕ был обёрнут никаким
   try/except — любое исключение здесь (в отличие от исключений внутри
   `DepotBuildWorker.run()`) раньше просто вылетало наружу необработанным.

**Исправлено (инструментирование, не гадательный фикс конкретной
строки — конкретная причина этого крэша по-прежнему НЕ подтверждена
логом, потому что лога не было):**
- `main_window.py::log_message()` теперь ПОМИМО памяти/виджета сразу
  дописывает (append+flush) каждую строку в `config.LOG_FILE` —
  частичный лог теперь переживает крэш, вместо того чтобы существовать
  только до нажатия кнопки "Сохранить", которое после крэша невозможно.
- `main.py::_install_crash_handler()` (новое) — глобальный
  `sys.excepthook`, ловит любое необработанное исключение (в первую
  очередь — то, что долетело до самого верха с ГЛАВНОГО потока, минуя
  все try/except ниже): пишет полный traceback с таймстампом в тот же
  `config.LOG_FILE`, показывает `QMessageBox.critical` с текстом
  ошибки и путём к логу (пользователь теперь видит ХОТЬ ЧТО-ТО вместо
  молчаливого исчезновения), затем всё равно зовёт
  `sys.__excepthook__` (не подавляет полностью — полезно при запуске
  через `python main.py` в разработке, где stderr реально виден).
  PyQt6 по умолчанию действительно прокидывает исключения из слотов в
  `sys.excepthook` (не `abort()`, как могло быть в некоторых связках
  PyQt5) — но так как нет Windows-машины под рукой, чтобы это
  перепроверить вживую на собранном `.exe`, это не единственная линия
  защиты, см. следующий пункт.
- `depot_tab.py::_on_scan_done()` — сборка `DepotConfirmDialog` теперь
  явно обёрнута в try/except (самый подозрительный конкретный код,
  см. пункт 3 выше) — при ошибке логирует, показывает
  `QMessageBox.critical` и корректно завершает воркер
  (`_on_finished(False, ...)`) вместо падения.
- **Проверено headless** (`QT_QPA_PLATFORM=offscreen`, с
  `QMessageBox.critical` замоканным, чтобы не блокировать тест
  модальным окном): (1) `log_message()` реально дописывает каждую
  строку на диск в `config.LOG_FILE`, немедленно, не дожидаясь
  "Сохранить лог"; (2) `sys.excepthook`, вызванный на синтетическое
  исключение, пишет полный traceback в файл и вызывает
  `QMessageBox.critical`; (3) синтетическое исключение внутри
  `DepotConfirmDialog.__init__` (подменённый класс) корректно ловится
  локальным try/except в `_on_scan_done()`, логируется, зовёт
  `_on_finished(False, ...)` — процесс остаётся живым, не падает.
- **Что дальше**: если крэш повторится — теперь `%APPDATA%\Uploder\
  uploader.log` должен содержать либо обычный ход событий вплоть до
  самого места падения (если сработал файловый лог, но само
  исключение всё равно как-то убило процесс раньше, чем успел
  сработать excepthook — маловероятно, но не исключено на native-крэш,
  который excepthook в принципе не ловит, см. ниже), либо явную запись
  "❌ НЕОБРАБОТАННОЕ ИСКЛЮЧЕНИЕ" с полным traceback — присылать именно
  этот файл при следующем повторении, вместо "приложение вылетело" без
  подробностей. **Открытый остаток**: `sys.excepthook` ловит только
  Python-исключения — настоящий native-крэш (сегфолт/access violation
  где-то внутри самого Qt/PyQt) им не перехватывается вообще; если
  проблема повторится и лог при этом останется пустым/оборванным на
  случайном месте без итоговой записи об исключении — это будет
  сигналом, что причина не в Python-коде, а глубже (драйверы/Qt/память
  системы), и потребует другого подхода (например, счётчика
  `progress.emit()` на такое количество файлов подряд — 173137 emit'ов
  за один проход — под вопросом на предмет реальной нагрузки на
  event-loop, не проверялось нагрузочно, только логическим разбором
  кода).

## НАЙДЕНА РЕАЛЬНАЯ ПРИЧИНА обоих крэшей: утечка QThread между сканированием и публикацией (2026-09-23, тем же вечером)

Живой повтор того же класса крэша ("хэшировалось — и пропало") — на этот
раз пользователь запускал приложение из обёртки с видимой консолью
(`=== TESL: update from git + launch ===`), и в консоли ПЕРЕД крэшем
буквально было видно:
```
QThread: Destroyed while thread '' is still running
```
Это не гипотеза, а точный диагностический вывод самого Qt — искать
причину дальше вслепую не понадобилось.

**Корень**: `DepotBuildWorker.run()` (`depot_sync_manager.py`) в
сканирующем заходе (вызывается без `confirmed_delta` — то есть именно
на этапе "Собрать и опубликовать" → сканирование компонентов) в конце
эмитит `self.scan_done.emit(...)` и просто возвращает управление —
**свой собственный сигнал `self.finished` в этой ветке НЕ эмитится
вообще** (эмитится только в ветке с `confirmed_delta is not None`, т.е.
на этапе реальной загрузки). А `_cleanup_thread()`
(`depot_tab.py`, quit()+wait()+обнуление `self._thread`/`self._worker`)
был подключён ТОЛЬКО через `_on_finished()`, которая сама вызывается по
подписке на `self._worker.finished` — то есть после успешного скана
этот сигнал никогда не приходит, и `self._thread`/`self._worker`
остаются висеть, указывая на QThread, чей `run()` уже реально
завершился (поток остановлен), но чья Qt-обёртка не была явно
`quit()`+`wait()`-нута.

Дальше пользователь видит `DepotConfirmDialog` (уже сканирование
закончено) и жмёт "🚀 Опубликовать" → `_start_upload()` первым делом
делает `self._thread = QThread()` — **последняя Python-ссылка на
СТАРЫЙ (сканирующий) QThread пропадает именно в этот момент**, объект
уходит в GC, пока Qt всё ещё считает его частью незавершённого потока
(assert/warning "Destroyed while thread '...' is still running") — на
части платформ/сборок PyQt это не просто предупреждение в консоль, а
`abort()` всего процесса. Это объясняет ОБА зафиксированных крэша
одинаково хорошо: первый (Skyrim, `--noconsole`-сборка, никакого следа
в логе) и второй (та же точка перехода скан→диалог→публикация, на этот
раз с видимой консолью и точным Qt-сообщением) — оба происходят РОВНО
на стыке "сканирование только что успешно завершилось → пользователь
подтвердил публикацию", что и объясняет специфичный паттерн
"хэшировалось-хэшировалось и вдруг пропало" лучше любой из более ранних
спекулятивных гипотез (`DepotConfirmDialog`'s try/except из раздела
выше остаётся как вторая линия защиты, но настоящая причина была не
там).

**Фикс**: `_on_scan_done()` теперь ПЕРВОЙ строкой вызывает
`self._cleanup_thread()` — к моменту, когда `scan_done` вообще долетел
до этого обработчика, `run()` сканирующего воркера гарантированно уже
вернул управление (иначе сигнал бы не пришёл), так что `quit()+wait()`
здесь безопасны и мгновенны, а `self._thread`/`self._worker`
корректно обнуляются ДО того, как `_start_upload()` (если пользователь
подтвердит) успеет создать новую пару — утечка закрыта структурно, не
патчем конкретного крэша.

**Урок**: любой QThread-воркер с несколькими возможными "выходами" из
`run()` (разные ветки, разные финальные сигналы) должен либо ВСЕГДА
эмитить один и тот же терминальный сигнал независимо от ветки, либо —
как здесь — вызывающая сторона должна подписываться на встроенный
`QThread.finished` (гарантированно приходит при любом завершении
`run()`), а не только на кастомный сигнал воркера, который может быть
эмитирован не во всех путях выполнения. Стоит перепроверить остальные
QThread-воркеры в этом репозитории (`ManifestManager`-подобные, если
появятся) на тот же паттерн "несколько ранних `return` из `run()`, не
все из которых гарантированно ведут к очистке потока на стороне GUI".

- **Проверено**: юнит-тест на подставном объекте потока (`quit()`/
  `wait()`/`isRunning()` — вызовы, а не реальный QThread, чтобы не
  зависеть от таймингов реальной сети/потоков в песочнице) подтверждает,
  что `_on_scan_done()` действительно зовёт `quit()`+`wait()` и
  обнуляет `self._thread`/`self._worker` ДО следующего шага. Реальный
  сквозной прогон (настоящие QThread + сеть до локальной тестовой
  панели) запускался, но зависал в headless offscreen-песочнице по
  причинам, не относящимся к самому фиксу (скорее всего к
  особенностям event loop в этом конкретном sandboxed окружении, не
  воспроизведено достаточно, чтобы утверждать что-то конкретное) —
  логика фикса проверена изолированно, а не полным интеграционным
  прогоном; следующий реальный крэш (если всё же повторится на
  свежем билде) теперь как минимум оставит запись в
  `%APPDATA%\Uploder\uploader.log` благодаря разделу выше.

## Упаковка чанков в pack-файлы (started 2026-09-23) — `pack_writer.py`

Прямой запрос пользователя: "настало время переписать менеджер для
заливки... вплоть до посекторной записи чанков, плюс чанки, размер
чанков, кластеры чанков, какая-то таблица чанков" — совпадает с уже
записанным ранее планом, см. `TESL/CLAUDE.md` "Живая диагностика
скорости установки", пункт 5: "упаковка чанков в несколько крупных
pack-файлов с индексом (chunk_id → файл+offset+длина, тот же принцип,
что git packfiles/Steam-подобные депо)" — было отложено тогда ("сначала
закрыть текущую цель — скачать и запустить сборку"), теперь цель
закрыта, начато.

**Формат**: `packs/pack-NNNNN.bin` (сырые конкатенированные байты
чанков, до `pack_size` каждый, по умолчанию 256MB) + `chunk_index.db`
(SQLite, `chunk_locations(chunk_id, pack, offset, size)`) в корне
проекта. НЕ заменяет старый `chunks/<xx>/<id>` протокол — опциональный,
включается через `config["use_packs"]=True`, существующая продакшен-
сборка на WebDAV в старом формате не трогается вообще.

**Новые файлы**:
- `pack_writer.py` — `PackWriter` (упаковка + дедуп + сплит по размеру),
  `write_chunk_index_db()`/`read_chunk_index_db()` (SQLite сериализация).
  Автономный, без сети — проверен отдельным синтетическим тестом
  (дедуп повторного `add_chunk`, сплит на несколько pack при маленьком
  `pack_size`, побайтовое восстановление каждого чанка по
  `(pack, offset, size)`, слияние индекса между "публикациями").
- `depot_sync_manager.py::DepotSyncManager.execute_sync_packed()` — та
  же delta-логика и та же структура `depot.json`/`versions/<key>.json`,
  что у `execute_sync()`, но загрузка байт чанков — через pack-файлы:
  скачивает существующий `chunk_index.db` (если есть), пакует ТОЛЬКО
  новые чанки (`delta.chunks_to_upload`, в `sorted()` порядке — том же,
  в каком лаунчер и так их запрашивает, см. TESL/core/chunk_installer.py
  — совпадение порядка упаковки с порядком чтения и есть весь смысл
  схемы), загружает pack-файлы + смёрженный (старое+новое) индекс.
  `DepotBuildWorker.run()` выбирает `execute_sync_packed` вместо
  `execute_sync`, если `config["use_packs"]` — иначе поведение НЕ
  меняется вообще.
- `publish_packed.py`/`publish_packed.bat` — CLI-обёртка (написана ДО
  того, как `depot_tab.py` была подключена к GUI в тот же день, см. ниже
  "Вкладка «Депо (chunks)» подключена к GUI" — оставлена в репозитории
  как более быстрый путь проверки без пересборки `.exe` через GitHub
  Actions, не единственный способ запустить публикацию больше).
  `.bat` спрашивает путь/URL панели/project/токен интерактивно, ничего
  не хардкодит.

**Читающая сторона (TESL-Panel)**: `/api/depot/<project>/<rel_path>` GET
теперь поддерживает настоящий HTTP Range (`send_file(...,
conditional=True)`, было `Response(data, ...)` — грузило файл целиком в
память при каждом чтении, для 256MB pack-файла ради одного чанка это
было бы катастрофой) — см. `TESL-Panel`'s CLAUDE.md.

**Проверено end-to-end** (2026-09-23, реальный локальный прогон, не
только синтетика): `publish_packed.py` против живого `TESL-Panel`
(своя тестовая инстанция) — 3 файла, упаковка в 2 pack (намеренно тесный
`--pack-size`, чтобы форсировать сплит), загрузка, затем независимая
проверка — Range-GET по каждой записи `chunk_index.db` вернул 206 и
байты, чей sha256 совпал с `chunk_id`. Повторная публикация того же
содержимого (delta) отдельно тестами `pack_writer.py` подтверждена
(0 новых чанков).

**НЕ сделано в этом заходе, сознательно**:
- Чтение упакованных депо со стороны лаунчера (TESL) — прямой запрос
  пользователя "пока не трогаем его, пока на второй пк не скачаю сборку
  старую" — дизайн продуман (новый `DepotClient.fetch_chunk_index_bytes()`
  с тем же try/404→fallback принципом, что уже есть у `manifest.db`;
  `ChunkInstaller` берёт ranged-GET для чанков, присутствующих в индексе,
  старый per-file GET — для остальных), не начато.

## Вкладка «Депо (chunks)» подключена к GUI (2026-09-23, тот же день)

Прямой запрос пользователя после того, как первая проверка упаковки
прошла через `publish_packed.py` — "сделай гуи". `depot_tab.py`
переработана и теперь ДЕЙСТВИТЕЛЬНО добавлена в `MainWindow.tabs`
(`main_window.py`, пункт "📦 Депо (chunks)") — раньше она существовала
в репозитории, но нигде не вызывалась (см. историю этого файла), теперь
реально открывается и работает из собранного `.exe`/`python main.py`.

**Что добавлено сверх исходной версии вкладки** (та могла только
WebDAV, без выбора backend'а, без поля локальной папки — `cfg.get
("local_dir")` в её `_start_build()` никогда не было бы `True`,
поскольку конфиг уже мигрировал на компонентную структуру, см.
`file_selector.py::_migrate_legacy` — вкладка была нерабочей ДАЖЕ если
бы её подключили как есть):
- Поле "Локальная папка" + кнопка "Обзор…" — своя, НЕ шарится с
  components у `ReleaseTab` (разные протоколы публикации, привязывать
  друг к другу не нужно).

## 🔴 Восстановление сборки из чанков — приоритет №1 (открыто 2026-09-21)

**Ситуация**: как минимум одна сборка (возможно `TESVAE`) была опубликована через
chunk-based депо-протокол (см. ниже) на реальный продакшен-сервер. Локальные
исходники этой сборки на машине оператора после этого были **утрачены**.
Единственная оставшаяся копия — чанки на сервере (`chunks/<xx>/<hash>` +
`versions/<key>.json` + `depot.json`). Ничего в текущем срезе кода эту сборку
из чанков обратно не собирает.

**Подтверждено на реальном сервере** (root shell пользователя,
`root@NETHUNTER-1:~# ls .../TESS/Instances/TESVAE/`):
```
chunks/  depot.json  versions/
```
`chunks/` — ровно 256 подпапок `00`…`ff` (двухсимвольные hex-префиксы хэшей —
content-addressed storage). `versions/` содержит `v1_20eb01df.json`.

**Схема на диске подтверждает chunk-протокол (`chunks/`+`versions/`), НО не
совпадает буквально ни с одним путём кода в этом репозитории целиком**:
- `chunk_manager.py::DepotManifest.build_id` генерируется как
  `uuid.uuid4().hex[:12]` (12 hex-символов), и `DepotSyncManager.execute_sync()`
  сохраняет версию как `versions/{build_id}.json` — БЕЗ префикса `v{N}_`.
- Реальный файл называется `v1_20eb01df.json` — 8 hex-символов после `v1_`.
  Это ТОЧНО совпадает с форматом `version_key` из ДРУГОГО, компонентного
  протокола (`release_manager.py::Release.version_key = f"v{build_number}_{build_id}"`,
  `build_id = uuid.uuid4().hex[:8]`) — но тот протокол вообще не создаёт `chunks/`
  и пишет манифесты в `manifests/`, а не в `versions/`.

**Вывод**: реальная сборка публиковалась какой-то ПРОМЕЖУТОЧНОЙ/более ранней
версией этого приложения — гибрид: chunk-хранилище физически (`chunks/` +
`versions/`), но с `v{build_number}_{build_id}`-нейминга версии (8-символьный id).

**СХЕМА ПОДТВЕРЖДЕНА, 2026-09-21, реальными данными** (пользователь выгрузил
содержимое `versions/v1_20eb01df.json` — 77МБ, слишком большой для прямой
вставки в чат, передан через Google Docs/Drive и разобран Python-скриптом на
стороне пользователя):
- Манифест версии — **не плоский `{"files": {...}}`**, а КОМПОНЕНТНЫЙ, как в
  `release_manager.py`: верхний уровень содержит `"components"` с ключами
  `Skyrim`/`MO2p`/`MO2ext` (совпадает с `config.py::COMPONENT_NAMES`), каждый —
  `{"included": bool, "file_count": int|null, "total_size": int|null,
  "files": {...}|null}`. В реальном файле `MO2ext` был `"included": false` —
  этот компонент не публиковался в этой сборке, соответственно у него нет
  файлов для восстановления.
- Поля отдельного файла внутри `files` — **буквально совпадают** с
  `chunk_manager.py::FileEntry`/`ChunkInfo.to_dict()`, адаптация НЕ
  понадобилась: `{"size": int, "hash": "<sha256 всего файла>", "chunks":
  [{"id": "<sha256 самого чанка>", "offset": int, "size": int}, ...]}`.
- Итог: гибрид подтверждён на уровне и структуры хранения (`chunks/`+`versions/`,
  chunk-протокол), и структуры самого манифеста версии (компонентная,
  `release_manager.py`-стиль) — ни `chunk_manager.py::DepotManifest`
  (ожидает плоский `files`), ни `release_manager.py::Release` (не знает про
  чанки вообще) не читают этот файл как есть. `chunk_id` = sha256 содержимого
  чанка — это уже встроено в `_download_chunk()` восстановителя ниже как
  верификация при каждой закачке (не отдельно проверялось на живых чанках
  до полного прогона, но проверяется автоматически на каждом чанке при
  восстановлении — расхождение сразу видно в логе, а не тихо портит файл).
- `depot_manifest.json` в `ls` действительно не было (см. ниже) —
  восстановитель идёт напрямую через `versions/<key>.json`, зная ключ
  (`v1_20eb01df`) явно, не полагаясь на "текущий" манифест.

**Восстановитель написан**: `depot_sync_manager/recover_from_chunks.py` (CLI,
без Qt-зависимости — можно гонять на голом Python 3.9+ с `requests`, без
установки всего репозитория). Логика (chunk-fetch → дедуп по пулу чанков →
параллельная закачка → сборка по `offset` → sha256-верификация целого файла)
переиспользует цикл `launcher_client.py::DepotClient.update()` — не переписана
с нуля, только адаптирована под явный выбор версии по ключу и под компонентную
структуру манифеста (`parse_version_manifest()` понимает ОБА варианта —
компонентный, реально найденный на сервере, и плоский `files`-верхнего-уровня
на случай другой сборки в чистом chunk-формате). Обязательно:
`--dry-run` (по умолчанию с проверкой наличия каждого чанка на сервере через
HEAD/Range-GET, БЕЗ скачивания тела) — гонять ПЕРВЫМ, до реальной закачки;
`--resume` включён по умолчанию — безопасно прерывать и перезапускать тем же
способом. Скрипт не хардкодит пароль — берёт `--password`, иначе
`TESL_DAV_PASSWORD` из окружения, иначе спрашивает через `getpass` (см. свой
собственный докстринг для точных примеров команд). Работает пользователь
на своей Windows-машине (см. "первый план это собрать из чанков сборку на
пк") — не запускался здесь ни разу вживую против реального сервера (нет
доступа к живым учётным данным из песочницы Claude, см. запись про
"Credential Materialization" — доступ к прод-WebDAV из сессии-песочницы
заблокирован классификатором инструментов намеренно, это не баг). Синтаксис
проверен (`python3 -m py_compile`), сеть — нет (недоступна из песочницы).
Логика `db.py`/`parse_version_manifest()` (включая ветку `MO2ext:
included=false` — именно тот случай, где у пользователя падал `StopIteration`
в собственном диагностическом скрипте) проверена офлайн-smoke-тестом на
синтетических данных в подтверждённой схеме (dedup чанков между файлами,
идемпотентность повторного `sync_release`, `recovery_runs` — всё прошло);
сетевая часть (`_download_chunk`/`check_chunk_exists`/реальный HTTP) не
тестировалась вообще, тестировать вживую может только пользователь.

## Локальный индекс релизов/чанков — `db.py` (SQLite, 2026-09-21)

По прямому запросу пользователя ("мб перенести это дело в бд", уточнено —
**операторский индекс внутри TESL-Manager, не источник истины для TESL**):
`depot_sync_manager/db.py`, SQLite-файл `%APPDATA%\Uploder\uploder.db` (см.
`config.DB_FILE`). Публикация на WebDAV (депо/манифесты/чанки) и то, что
читает TESL — **не меняются вообще**, эта БД параллельна им, только для
запросов на стороне оператора. Полное обоснование границ — в докстринге
самого `db.py`, не дублирую здесь; коротко: таблицы `releases`/`components`/
`files`/`chunks` — нормализованный слепок того, что видели на сервере
(по одной версии на строку в `releases`, файлы и их чанки — отдельными
таблицами, а не JSON-блобом), плюс `recovery_runs` — журнал запусков
`recover_from_chunks.py` (dry-run и реальных, с итоговыми числами).
`chunk_reuse_stats()` — какие чанки повторяются МЕЖДУ версиями (полезно
для будущей мультисборочности — оценить, сколько реально нового трафика
требует публикация поверх уже имеющихся на сервере чанков).

**Интеграция пока только в `recover_from_chunks.py`** (сам скрипт заносит
разобранный манифест версии и итоги своего запуска автоматически, если не
передан `--no-db`) — это единственный CLI-путь, который сейчас активно
используется (приоритет №1). `release_manager.py`/`depot_sync_manager.py`
(публикация из GUI) в эту БД пока НЕ пишут — сознательно не трогал
публикующий путь в этом же заходе, чтобы не смешивать с срочной задачей
восстановления; когда дойдут руки на мультисборочность (см. ниже), логично
завести туда запись через тот же `db.sync_release()` при каждой публикации
релиза — модуль для этого уже готов, просто не подключён.

## РЕАЛЬНАЯ схема depot.json подтверждена + смена плана: manifest.db читает сам лаунчер (2026-09-21, тот же день)

- Пользователь выгрузил РЕАЛЬНЫЙ `depot.json` (653 байта, через Google
  Drive) — впервые полное содержимое, не гипотеза. Схема ОТЛИЧАЕТСЯ от
  ОБОИХ вариантов, которые `recover_from_chunks.py::resolve_version()`
  (тогда ещё `resolve_version_path()`) проверял:
  ```json
  {
    "versions": {
      "v1_20eb01df": {
        "label": "v1_20eb01df", "build_number": 1, "build_id": "20eb01df",
        "channel": "stable", "created_at": "...", "file_count": 173137,
        "total_size": 171046874997, "chunk_count": 155290,
        "manifest": "versions/v1_20eb01df.json",
        "components": {"Skyrim": {"included": true}, "MO2p": {"included": true}, "MO2ext": {"included": false}}
      }
    },
    "current": {}, "app_id": "app", "updated_at": "..."
  }
  ```
  `"current": {}` — ПУСТ (версия физически лежит на сервере, но ещё не
  активирована ни на одном канале). Билд крупный: 173137 файлов,
  ~171GB суммарно, 155290 уникальных чанков.
  **Найдена и исправлена реальная ошибка**: `resolve_version_path()`
  проверял только `current`-only-компонентный и `channels`-only-chunk
  гипотезы — ни одна не матчится с реальной `versions`+`current` схемой
  (`current` при этом может быть пустым), автоопределение версии без
  явного `--version-key` бы просто отказало на реальном сервере.
  Переименован в `resolve_version()`,
  теперь ПЕРВЫМ делом проверяет `versions`-схему (единственная версия при
  пустом `current` берётся автоматически, с явным предупреждением в лог),
  старые две гипотезы остались вторым/третьим fallback на случай другой
  сборки. Проверено офлайн мокнутым `fetch_json` на РЕАЛЬНОМ содержимом
  depot.json (не синтетике) — резолвится верно.
  **Приятное совпадение**: TESL'а собственный `core/depot_client.py`
  (`get_versions()`/`get_current_version()`/`get_version_info()`) с
  самого начала предполагал именно эту `versions`+`current` схему —
  только код восстановителя в ЭТОМ репозитории гадал неправильно.

- **Прямой запрос пользователя, меняющий архитектуру**: "сделай одноразовый
  конвертор чтобы внести данные в файл бд а затем его лаунчером зацепим с
  вебдава" — т.е. `manifest.db` (SQLite) — не только операторский индекс
  (`uploder.db` выше), но и артефакт, который **сам ЛАУНЧЕР** скачивает с
  WebDAV и использует для установки, напрямую из уже существующих на
  сервере `chunks/` — оператору НЕ нужно пересобирать всю сборку
  (~171GB) локально и заливать её обратно на WebDAV под старым
  компонентным протоколом. Подтверждено пользователем: "депо менеджер
  теперь пишет все эти данные в depo.db, у каждой сборки он свой, и для
  нашей уже существующей мы создаём этот файл из тех что имеем и я его
  закидываю в вебдав, ты допиливаешь лаунчер и я скачиваю сборку которая
  собирается из чанков".

- **`depot_sync_manager/build_manifest_db.py`** (новый, "одноразовый
  конвертор") — читает `depot.json` + `versions/<key>.json` (оба уже
  локально) и пишет компактный `manifest.db` (SQLite, схема: `meta`
  один-ряд-метаданные + `files`(component,path,size,hash) +
  `chunks`(component,path,chunk_id,offset,size)) — **намеренно отдельная
  схема от `uploder.db`** (без `raw_json`/`recovery_runs` — публиковать
  пользователям сырой 77МБ JSON ЕЩЁ РАЗ внутри БД смысла нет, только
  раздувает файл). Предупреждает, если depot.json заявляет другое число
  файлов/чанков, чем реально разобралось в манифесте версии (тот же
  drift-check, что в `ingest_local.py`).
  **Конвенция имени публикации**: `manifest.db` заливается на WebDAV
  РЯДОМ с JSON-манифестом версии, тот же путь, расширение `.db` вместо
  `.json` (`versions/v1_20eb01df.json` → `versions/v1_20eb01df.db`) — это
  единственное, что TESL проверяет для автоопределения, никакое новое
  поле в `depot.json` не требуется. **Значит `--out` конвертора должен
  называться так же** — если назвать файл иначе, лаунчер его не найдёт.
- **`depot_sync_manager/ingest_local.py`** (новый, попутно) — то же самое
  чтение локальных `depot.json`/`versions/<key>.json`, но пишет в
  ОПЕРАТОРСКИЙ `uploder.db` (не в публикуемый `manifest.db`) — для тех
  случаев, когда нужен только запрашиваемый индекс на машине оператора,
  без публикации. Поддерживает частичный режим (только `depot.json`, без
  большого файла версии — заносит агрегаты, `files_synced=0`, полный sync
  потом дополняет, не теряя уже известное) — `db.sync_release()` ради
  этого получил `entries: Optional[...]`/`declared_*`/`components_meta`
  параметры (раньше `entries` был обязателен). Использован для реального
  `depot.json` этой сборки — `releases.files_synced=0` до тех пор, пока
  кто-то не прогонит с `--version-json` против настоящего (не синтетического)
  77МБ файла.
- **TESL (лаунчер) — своя половина сделана в том же заходе**, см. его
  собственный `CLAUDE.md` "Chunk-протокол на стороне лаунчера":
  `core/chunk_manifest_db.py` (чтение `manifest.db`),
  `core/chunk_installer.py` (без Qt, диф/докачка/сборка/верификация/
  чистка — то же самое, что `ChunkRecoverer.recover()` здесь, но для
  установки клиенту, а не восстановления оператору), `core/depot_client.py`
  (`fetch_manifest_db_bytes()`/`download_chunk()`), `core/workers.py`
  (`DownloadWorker` пробует chunk-протокол первым, 404 → тихий откат на
  старый плоский путь, `main_window.py` вообще не тронут).
- **Реальный 77МБ `versions/v1_20eb01df.json` до сих пор не обработан ни
  этим репозиторием, ни лаунчером** — только его РЕАЛЬНЫЕ метаданные из
  `depot.json` (агрегаты) и синтетические per-file данные (для
  smoke-тестов, структурно совпадающие со схемой, но не настоящее
  содержимое). Причина всё та же: файл физически слишком большой, чтобы
  Claude мог получить его полное содержимое через доступные инструменты
  (Google Drive `download_file_content` отдаёт файл целиком одним base64
  в ответ инструмента — для 77МБ это ~100+МБ текста в контексте, не
  вариант). **Следующий шаг — за пользователем**: прогнать
  `build_manifest_db.py --depot-json depot.json --version-json
  v1_20eb01df.json --out v1_20eb01df.db` на своей машине (или там, где
  реально лежат оба файла), залить `v1_20eb01df.db` на WebDAV рядом с
  `versions/v1_20eb01df.json`, и попробовать установку через TESL.

## Компонентный протокол (текущий, подключён к UI — `release_manager.py`)

```
<remote_path>/
  depot.json                    # {app_id, current: {channel: version_key}, versions: {...}}
  manifests/<version_key>.json  # полный манифест версии (+ components-секция)
  manifest.json                 # копия манифеста текущей stable-версии (совместимость)
  files/<Skyrim|MO2p|MO2ext>/<rel_path>
  poster.png
```
Компонент, не включённый в релиз (`included: false`), клиент (TESL) не трогает —
оставляет то, что уже стоит от предыдущей версии. `version_key` = `v{build_number}_{build_id}`,
`build_id = uuid.uuid4().hex[:8]`. Это протокол, который реально понимает TESL
(`core/depot_client.py`) — **но НЕ протокол, которым была опубликована сборка,
чьи чанки лежат на сервере** (см. выше). Пока восстановление не сделано, TESL
физически не может поставить эту сборку пользователям.

## Chunk-based протокол (дормантный в UI, но реальные данные на сервере — см. выше)

```
<remote_path>/
  depot.json              # {app_id, depot_id, channels: {channel: {build_number, build_id, manifest, ...}}}
  depot_manifest.json     # текущий актуальный манифест (не найден в последнем ls — под вопросом)
  versions/<build_id>.json  # история версий, полный DepotManifest
  chunks/<xx>/<chunk_id>   # content-addressed блоки (chunk_id = sha256(содержимого))
```
`depot_tab.py` (вкладка, работающая с этим протоколом) **теперь подключена**
к `MainWindow.tabs` (пункт "📦 Депо (chunks)", см. "Вкладка «Депо (chunks)»
подключена к GUI" ниже, 2026-09-23) — публикация новых сборок через этот
протокол доступна из интерфейса. Открытый вопрос "стоит ли слить два
параллельных протокола (этот и компонентный `release_manager.py`) в
один" остался нерешённым — сознательно не трогался в этом заходе, не
путать с ним.

## Read-only nginx + Cloudflare перед прямым WebDAV-чтением (план, начато 2026-09-22)

Живой контекст: пользователь пожаловался на низкую скорость установки
(~10-13 MB/s на гигабите+SSD) — реальный баг нашли и починили на стороне
TESL (сборка файлов сериализовалась на одном потоке, см. TESL/CLAUDE.md
"Скорость chunk-установки..."), но заодно всплыл более общий вопрос:
можно ли раздавать депо быстрее/надёжнее в принципе, "как в Стиме".

**Анализ, что реально даёт Стиму скорость**: не экзотичный протокол, а
(1) верификация чанков по хэшу (у нас УЖЕ есть — `chunk_manager.py`/
`DepotClient.download_chunk()` — "битых файлов" архитектурно не должно
быть) и (2) CDN с точками присутствия по всему миру. У нас — один сервер
без CDN; собственные замеры в `depot_sync_manager.py`'s докстринге уже
показывают, что ОДНО PUT-соединение даёт ~79 MB/s локально — то есть
потолок скорости определяется физическим каналом ЭТОГО сервера, не
протоколом (WebDAV/HTTP/что угодно). Смена языка (Rust и т.п.) этот
потолок не поднимет — а вот CDN перед раздачей поднимает, причём
бесплатно (Cloudflare free tier).

**Решение, выбранное пользователем**: тот же физический сервер (Debian
13, root по SSH подтверждён), что уже хостит продакшен Nextcloud/WebDAV
и ДРУГОЙ, не относящийся к этому проекту сайт — оба трогать нельзя (свои
сертификаты через certbot, свой веб-сервер). Поэтому:

- **Паблиш (запись) остаётся полностью без изменений** — TESL-Manager
  как публиковал новые версии через WebDAV PUT/MKCOL в Nextcloud, так и
  продолжает. Ни строчки кода в `release_manager.py`/
  `depot_sync_manager.py` не меняется.
- **Добавляется отдельный read-only nginx** (свой порт/поддомен, не
  трогает существующий веб-сервер/сертификаты) — раздаёт ТЕ ЖЕ файлы,
  что уже лежат в Nextcloud, но читая их **напрямую с диска** (Nextcloud
  storage: `<datadirectory>/<WebDAV-логин>/files/<путь>`), минуя
  PHP/WebDAV-стек целиком для самого частого и тяжёлого пути — чтения
  чанков лаунчером.
- **За nginx — Cloudflare (проксирование, "оранжевое облако")**, TLS на
  edge, origin — Cloudflare Origin Certificate (не certbot, не конфликтует
  с существующими сертификатами на этой же машине). Content-addressed
  чанки (путь = хэш содержимого) отдаются с `Cache-Control: immutable,
  max-age=1 год` — Cloudflare кэширует их на edge НАВСЕГДА без единой
  строчки нового кода в лаунчере/менеджере — это и есть тот самый "CDN
  как у Стима", бесплатно. `depot.json`/`versions/*.json`/`*.db` (МЕНЯЮТСЯ
  при каждом релизе) — короткий TTL (60с), чтобы лаунчер не залипал на
  старой версии надолго.
- **Критичная проверка перед разворачиванием**: если в Nextcloud включено
  server-side encryption, файлы на диске — зашифрованные блобы, читать их
  в обход WebDAV нельзя (получили бы мусор вместо чанков). Скрипт
  (`infra/setup_depot_nginx.sh`) сам проверяет `occ encryption:status` и
  ОТКАЗЫВАЕТСЯ работать, если включено, а не тихо разворачивает
  нерабочую раздачу.
- Basic Auth (`htpasswd`) на nginx — тот же логин/пароль, что уже зашит в
  лаунчер как `DAV_USERNAME`/`DAV_PASSWORD` (тот же принцип "не секрет в
  строгом смысле", см. TESL/CLAUDE.md "Секреты и их модель угроз") — так
  клиентский код в `depot_client.py` не меняется ВООБЩЕ, меняется только
  значение `DAV_BASE_URL` (когда пользователь подтвердит, что новый
  эндпоинт реально отдаёт валидные данные — этот переключатель НЕ сделан
  в этом же заходе, чтобы не выкатить пользователям указатель на ещё не
  проверенный сервер).
- Файлы: `depot_sync_manager/infra/nginx-depot-read.conf.template`
  (плейсхолдеры `__X__`, реальные домен/пути НЕ коммитятся — см. верх
  этого файла про ДСП) + `depot_sync_manager/infra/setup_depot_nginx.sh`
  (разворачивает: находит `occ`/datadirectory, проверяет encryption,
  ставит nginx, генерирует конфиг из шаблона, поднимает). Выполняется
  оператором вручную на сервере (root по SSH) — у Claude-сессии нет
  exec-доступа к продакшену, тот же принцип, что и во всех остальных
  репозиториях этого engagement'а.
- **Всё, что относится к этому сервису, живёт в `/opt/tesl-depot`**
  (прямой запрос пользователя, не разбрасывать по `/etc`) — сертификат/
  ключ (`ssl/origin.{pem,key}`), htpasswd, и сам реальный файл nginx-
  конфига (`nginx/<домен>.conf`). Единственное исключение — симлинк в
  `/etc/nginx/sites-enabled/<домен>.conf`, указывающий на файл внутри
  `/opt/tesl-depot/nginx/` — сам nginx (стандартный `include
  /etc/nginx/sites-enabled/*;` в его `nginx.conf` на Debian) конфиги
  подхватывает только оттуда, это неизбежный минимум. Весь каталог
  переопределяется флагом `--project-dir` скрипта.
- **`--alias-path` — найдено вживую при первом реальном запуске
  (2026-09-22): WebDAV-корень депо на этом сервере смонтирован в
  Nextcloud как External Storage (Local), а не лежит внутри "родного"
  datadirectory.** `occ config:system:get datadirectory` отдаёт только
  путь родного хранилища — где физически на диске примонтировано ВНЕШНЕЕ
  хранилище, это отдельная запись в БД Nextcloud (`oc_storages`/
  `oc_mounts`), которую эта команда не видит вообще; скрипт изначально
  предполагал `<datadirectory>/<nc-user>/files/<depot-subpath>` (верно
  только для родного хранилища) — с external storage это давало
  несуществующий путь. Добавлен флаг `--alias-path` — передаёт реальный
  путь на диске напрямую, в обход всей datadirectory-логики (шаги
  occ/encryption всё равно выполняются как раньше, они не связаны с этим
  выбором); `--depot-subpath` в этом случае не нужен. Найти реальный
  путь на сервере, если он тоже на external storage — `df -h` + `ls` от
  корня подходящего смонтированного диска вниз, пока не увидишь папку с
  `chunks/` внутри (сам скрипт после `--alias-path` проверяет именно
  это, а не просто существование директории).
- **Не сделано в этом заходе, следующие шаги**: (1) пользователь
  запускает `setup_depot_nginx.sh` на реальном сервере, проверяет `curl`
  вручную; (2) настраивает Cloudflare (DNS-запись, Origin-сертификат,
  Cache Rule — все шаги описаны в выводе скрипта); (3) после
  подтверждения, что всё реально работает — правится `TESL/launcher/
  config.py::DAV_BASE_URL` (возможно, заодно переименовать из `DAV_*` во
  что-то менее WebDAV-специфичное, раз это уже не WebDAV — не решено).
  До этого момента лаунчер продолжает читать напрямую из Nextcloud
  WebDAV, как сейчас — ничего не сломано, миграция строго аддитивна.

## Веб-панель — начато 2026-09-23 (`scp-oss/TESL-Panel`, отдельный репозиторий)

Прямой запрос пользователя, отменяет прошлую отметку "отложено" ниже:
поднять сервис с (1) страницей скачивания `TESL.exe`/`TESL-Manager.exe`
(источник — GitHub Releases обоих репозиториев) и (2) API прямой
публикации новых сборок, в обход Nextcloud/WebDAV, хранилище на диске
сервера — путь ДСП (см. `panel.env`, не в git), задаётся оператором при
деплое `TESL-Panel/infra/deploy.sh`.

**Эта сторона (TESL-Manager)** получила новый транспорт-класс —
`panel_client.py::PanelHTTP` — реализующий ТОТ ЖЕ интерфейс, что
`depot_sync_manager.py::NextcloudDAV` (`exists`/`mkcol`/`put`/`put_file`/
`get_bytes`/`list_chunk_ids`/`test_connection`/`close`). `DepotSyncManager.
_get_dav()` теперь смотрит на `config["backend"]` (`"webdav"` — умолчание,
без изменений; `"panel"` — новый) и конструирует нужный транспорт —
`execute_sync()`/`ensure_depot_structure()`/весь остальной код публикации
НЕ ИЗМЕНИЛСЯ ни на строчку, это чисто swap транспорта снизу.

Конфиг для панели — новый ключ `"panel"` (параллельно `"webdav"`):
```json
{
  "backend": "panel",
  "panel": {
    "base_url": "https://<домен панели>",
    "project":  "TESVAE",
    "token":    "<upload-токен, см. вывод TESL-Panel/infra/deploy.sh>"
  }
}
```
**GUI подключён (2026-09-23)** — `depot_tab.py` теперь в `MainWindow.tabs`
("📦 Депо (chunks)"), с полями выбора backend'а (TESL-Panel/WebDAV) и
panel_url/project/token прямо в форме — см. "Вкладка «Депо (chunks)»
подключена к GUI" ниже за подробности. До этой правки backend/panel-конфиг
можно было задать только вручную в `config.json` или программно
(`publish_packed.py`) — теперь это не единственный путь.

**Проверено сквозным тестом** (синтетические файлы → `ChunkManager.
scan_directory` → `DepotSyncManager(backend="panel")` → реальный Flask-
сервер `TESL-Panel` на `127.0.0.1` → файлы физически на диске, включая
`chunks/`+`versions/<id>.json`+`depot.json`) — публикация и повторная
публикация того же содержимого (0 новых чанков, delta корректно увидел
уже загруженные chunk_id через новый `list_chunk_ids()`) прошли без
единой правки в `execute_sync()`. Подробности теста и API — см.
`TESL-Panel`'s собственный CLAUDE.md.

**Уже опубликованная на WebDAV сборка не трогается** — переключение
происходит только для СЛЕДУЮЩЕЙ публикации, которую оператор явно
выберет опубликовать через `backend: "panel"`; существующие чанки на
Nextcloud остаются на месте, TESL-лаунчер по-прежнему читает их оттуда
(его `DAV_BASE_URL` не менялся, прямой запрос пользователя "лаунчер тоже
пока в таком виде").

## build_id вместо имени как ключ + полноценное управление сборками (2026-09-23, пятый заход)

Прямой запрос пользователя, продолжение предыдущего захода (выбор
сборки на "Релизы"): "проект в панели и в менеджере не надо указывать
как ключ, т.к. проекты мы создаём и в панели, и в менеджере... менеджер
у нас — средство коммуникации сборки со стороны дева плюс пульт от
функционала панели, сборки — это объекты внутри". Уточнено вопросом:
выбран вариант "полноценно — SQLite в панели, id реальный ключ" (та
задумка с `chunk_index.db` как отдельным локальным файлом ПЕР-СБОРКУ
остаётся нетронутой, это другой вопрос, см. TESL-Panel's CLAUDE.md) +
менеджер получает полное управление сборками (создать/удалить/
переименовать), не только выбор.

- **`panel_client.py::PanelHTTP`** — параметр `project` переименован в
  `build_id` (конструктор, все внутренние URL) — это реальный ключ во
  всех `/api/depot/<build_id>/...` запросах, зеркалит TESL-Panel's
  `builds_db.py`. `list_projects()`/`create_project()` заменены на
  `list_builds()` (возвращает `[{"id","name","created_at"}]`, не голые
  строки), `create_build(name) -> (dict|None, error)`, плюс новые
  `delete_build(build_id) -> bool` и `rename_build(build_id, new_name)
  -> (bool, msg)` — бьют в новые `/api/builds`/`/api/builds/<id>`
  DELETE/PATCH на панели.
- **Конфиг**: `cfg["panel"]["project"]` (строка-имя) заменена на
  `cfg["panel"]["build_id"]` (реальный ключ, UUID) +
  `cfg["panel"]["build_name"]` (закэшированное имя для отображения —
  `DepotManifest.app_id`, `StatusBar.set_backend()` — без лишнего
  сетевого похода за именем на каждый рендер статус-бара).
- **`DepotTab`'s блок "Сборка"** (был добавлен предыдущим заходом с
  просто выбором) — `build_combo` теперь хранит `build_id` в itemData
  (`Qt.ItemDataRole.UserRole` по умолчанию у `QComboBox.addItem(text,
  data)`), показывает имя как текст. Добавлены "✏️ Переименовать" и
  "🗑 Удалить" рядом с существовавшими "🔄"/"➕ Новая" — `_rename_current_
  build()`/`_delete_current_build()`, тот же паттерн, что и создание
  (диалог → вызов API → `_refresh_builds()`). `DepotFilesTab`'s
  независимый `project_combo` (выбор сборки для ПРОСМОТРА файлов, не
  обязательно текущей сборки публикации) обновлён так же —
  `currentData()`/`findData()` вместо `currentText()`/`findText()`.
- **Живой баг, найденный интеграционным тестом**: `QComboBox.
  setCurrentIndex(idx)` не эмитит `currentIndexChanged`, если `idx` уже
  совпадает с текущим индексом — а именно так и происходит сразу после
  `_refresh_builds()`, потому что Qt сам выставляет `currentIndex = 0`
  при первом `addItem()` в пустой комбобокс (даже под `blockSignals
  (True)`, это не сигнал, а реальное состояние). Итог: после `_create_
  new_build()` только что созданная сборка визуально выбиралась в
  комбобоксе, но `_save_build_choice()` (подписанный на сигнал) никогда
  не срабатывал — `cfg["panel"]["build_id"]` оставался пустым/старым, и
  следующая публикация ушла бы не в ту сборку (или ни в какую — провал
  валидации). Исправлено явным вызовом `self._save_build_choice()` в
  конце `_refresh_builds()`/`_create_new_build()`/`_rename_current_
  build()` — не полагаться на сигнал после любой операции, которая сама
  меняет содержимое комбобокса. **Урок**: `setCurrentIndex()` после
  `clear()`+`addItem()` — в принципе ненадёжный способ гарантировать,
  что подписчик на `currentIndexChanged` увидит новое состояние; если
  где-то ещё в этом GUI есть похожий паттерн (комбобокс, перезаполняемый
  программно, с логикой в обработчике сигнала выбора) — стоит явно
  проверить тем же способом (реальный интеграционный тест, не просто
  "код не упал").
- **Миграция конфига** (`MainWindow._migrate_legacy_backend_config()`)
  расширена: если `cfg["panel"]["project"]` (старый строковый формат)
  присутствует, а `"build_id"` ещё нет — `project` убирается (нельзя
  надёжно превратить старое имя в id офлайн, без сетевого похода на
  панель при каждом старте), `build_id`/`build_name` выставляются в
  пустую строку. Пользователю нужно один раз заново выбрать сборку в
  комбобоксе на "Релизы" — список сам подтянется, тот же UX, что и при
  первом использовании. **Живой баг той же природы, что и в TESL-Panel's
  собственной миграции**: этот блок изначально стоял ПОСЛЕ `if not old:
  return` (old = `cfg["depot_tab"]`), так что для конфигов без
  `depot_tab` (уже в верхнеуровневом формате с этой же сессии) новая
  миграция вообще не запускалась — сама эта функция получила свой ранний
  `return`, разбитый на два независимых блока вместо одного общего.
- **`publish_packed.py`** (CLI, standalone) — `--project` остаётся
  именем (для удобства командной строки), но перед публикацией
  резолвится через новый `PanelHTTP.list_builds()`/`create_build()` —
  ищет сборку с таким именем, создаёт при отсутствии, дальше работает с
  её `id`.
- **Проверено**: полный сквозной GUI-тест против реального локального
  Flask (TESL-Panel) — подключение по коду настройки → создание сборки
  через `DepotTab` → сканирование компонентов → публикация (`packed`) →
  переименование (папка на диске физически переехала, файл остался
  читаемым по тому же `build_id`) → удаление, плюс отдельно оба пути
  миграции конфига (`cfg["depot_tab"]`-вложенный старый формат и плоский
  `cfg["panel"]["project"]`-формат из предыдущего захода тем же вечером).

## Алгоритм заливки под SSD/HDD (2026-09-24)

Прямой запрос: объяснить текущий алгоритм заливки чанков и сделать два
режима — для SSD и для HDD сервера, с тщательной проработкой HDD-режима
ради максимума производительности и на заливке, и на последующем
скачивании лаунчером.

**Как было устроено до этого (оба протокола уже существовали)**:
- `execute_sync()` (старый, per-chunk) — каждый новый chunk_id льётся
  отдельным `PUT` в `chunks/<xx>/<id>`, параллельно
  (`ThreadPoolExecutor(max_workers=4)`, `as_completed` — порядок
  завершения произвольный). На диске сервера в итоге — множество мелких
  файлов в случайном порядке появления.
- `execute_sync_packed()` (дефолт) — чанки читаются локально в порядке
  `sorted(chunk_id)` (== порядок, в котором лаунчер их запрашивает при
  установке, см. `TESL/core/chunk_installer.py` — совпадение специально
  сохраняется, это и есть весь смысл упаковки), пишутся подряд в
  `pack-NNNNN.bin`, готовые pack-файлы заливались **строго
  последовательно, один PUT за раз** — параллелизма между pack-файлами
  не было вообще, независимо от типа диска на сервере.

**Физика, почему это важно именно для HDD**: на вращающемся диске seek
(перемещение головки) стоит на порядки дороже, чем сам по себе
последовательный throughput — случайный доступ или конкурентная запись
в РАЗНЫЕ файлы с разных потоков заставляет головку метаться между
позициями, разрушая скорость по сравнению с одним непрерывным потоком
записи. Именно эта физика уже была причиной появления самого
`pack_writer.py` (см. "Упаковка чанков в pack-файлы" выше —
iostat-подтверждение случайного чтения на реальном сервере
пользователя). SSD, наоборот, не деградирует от случайного/конкурентного
доступа (seek ~0) — там узкое место обычно сеть/CPU, и НЕ использовать
параллелизм означает просто зря недогружать канал.

**Реализовано — два явных режима, `depot.disk_mode` ("hdd" | "ssd",
дефолт "hdd")**:
- **HDD** (`pack_writer.py::HDD_PACK_SIZE = 1GB`, было
  `DEFAULT_PACK_SIZE = 256MB`) — заливка pack-файлов остаётся строго
  последовательной (один `PUT` за раз, как и раньше), но сам pack-файл
  стал КРУПНЕЕ. Причина увеличить размер именно для HDD: каждый новый
  файл на диске сервера — это операции с метаданными ФС (создание
  inode/записи каталога), которые сами по себе требуют seek, отдельно
  от содержимого файла — меньше файлов на тот же объём данных, меньше
  таких пауз. Порядок записи (`sorted(chunk_id)`) не менялся — это
  критично и для СКАЧИВАНИЯ: раз лаунчер читает чанки в том же порядке,
  Range-GET по большому pack-файлу на сервере тоже получается
  последовательным чтением, а не случайным — весь смысл рушится, если
  порядок записи разойдётся с порядком чтения.
- **SSD** (`DEFAULT_PACK_SIZE = 256MB`, как было) — заливка
  pack-файлов теперь **параллельная**
  (`UPLOAD_WORKERS_PACKS_SSD = 4`, `ThreadPoolExecutor` + `as_completed`,
  тот же паттерн, что уже использует старый per-chunk протокол для
  своих 4 потоков через тот же `dav`-клиент — `requests.Session` в
  `NextcloudDAV`/`PanelHTTP` уже настроен на конкурентные запросы,
  ничего дополнительно готовить не пришлось).
- **Автовывод параметров из ОДНОГО выбора** — прямое продолжение
  "настройки депо должны определяться автоматически" (см. выше):
  единственная ручная настройка — сам тип диска (это физический факт
  про СЕРВЕР, который невозможно ни вывести из конфига, ни замерить
  с клиента без доступа к нему), размер pack-файла и параллелизм
  заливки выводятся из этого одного выбора автоматически, а не
  выставляются отдельными полями. `DepotSyncManager.__init__`:
  `_auto_pack_size = DEFAULT_PACK_SIZE if disk_mode=="ssd" else
  HDD_PACK_SIZE`, `pack_size = config.get("pack_size") or
  _auto_pack_size` — явный `pack_size` в конфиге (если вдруг остался
  от старой версии) по-прежнему побеждает автовывод.
- **Дефолт — "hdd"**, сознательно консервативный выбор: ошибиться в
  сторону последовательной заливки на SSD стоит немного скорости,
  ошибиться в сторону параллельной заливки на HDD — реальная деградация
  производительности сервера (та самая, которую весь этот механизм
  изначально появился решать).
- **UI**: единственный новый контрол в "⚙️ Настройки" — "🖴 Тип диска
  на сервере" (`QComboBox`, HDD/SSD), сохраняется в
  `cfg["depot_publish"]["disk_mode"]` — тот же ключ конфига, что раньше
  занимали убранные ручные настройки chunk_size/pack_size/use_packs, но
  теперь это одно осмысленное решение вместо нескольких сырых чисел.
- **Прогресс-бар** (проценты/скорость/ETA, см. раздел выше) работает
  одинаково в обоих режимах — для SSD агрегирует скорость по мере
  завершения параллельных заливок (`as_completed`), не только по одному
  файлу за раз.
- **Проверено**: юнит-тест деривации `pack_size` из `disk_mode` (4
  сценария — дефолт/явный hdd/явный ssd/явный `pack_size` побеждает);
  headless-тест UI-контрола (дефолт hdd, сохранение при смене, загрузка
  сохранённого значения при перезапуске, прокидывание в
  `_build_runtime_config()`); **реальный сквозной прогон против
  локального `TESL-Panel`** для ОБОИХ режимов — 6 файлов, форсированный
  маленький `pack_size`, чтобы получить несколько pack-файлов, — оба
  режима успешно публикуют (`execute_sync_packed()` реально отработал),
  `chunk_index.db`, скачанный обратно с сервера, содержит все 12
  чанков с корректными `(pack, offset, size)`.
- **Не сделано в этом заходе, открытый вопрос**: чтение (скачивание
  лаунчером) уже физически последовательно на уровне ЗАПИСИ (порядок
  чанков в pack совпадает с порядком чтения), но сама читающая сторона
  (Range-GET на TESL-Panel) не различает HDD/SSD режим — да и не
  должна: она просто отдаёт диапазон байт из уже готового файла,
  выигрыш от правильного disk_mode достигается ЦЕЛИКОМ на этапе
  публикации (как физически легли данные), не на этапе чтения.

## Стиль

PyQt6, `QThread` + `moveToThread`, сигналы `pyqtSignal` для логов/прогресса/`finished`.
Русскоязычные строки логов/UI — сохраняем стиль при доработках.
